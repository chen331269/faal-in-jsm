## 一、程序里到底有几个线程

| 线程 | 干什么 | 位置 |
|---|---|---|
| 主线程 | 读命令行输入、加载配置、执行命令 | `main.cpp:3785` 的 `while (!quit)` |
| **输入轮询线程** | 每 1 ms 读手柄、跑整套映射和 **FAAL**、发鼠标事件 | `SDLWrapper.cpp:567` 创建 → `pollDevices()` |
| AutoLoad 线程 | 每秒检查前台窗口，切换配置 | `main.cpp:3259` |
| 遥测 | 每帧发 UDP（你配置里 `TELEMETRY_ENABLED=ON`） | `main.cpp:1327` |

**FAAL 全部跑在“输入轮询线程”上**，而“改参数”发生在主线程。
两者之间**没有**任何锁——这就是下面几个问题的根源。

## 二、问题清单（按“你会不会遇到”排序）

### 1. 退出时堆损坏 —— 实测确认，正常退出必现

`SettingsManager` 把 12 个 FAAL 全局设置对象交给 `shared_ptr` 托管（`SettingsManager.cpp:27`），
程序退出时会对**静态存储地址**执行 `delete`。

- 证据：用同样模式写了一个 10 行程序，退出时返回 `0xC0000374`（堆损坏），缓冲区输出丢失。
- 你会看到：关 JSM 时偶发“已停止工作”，或者什么也看不到（进程已经退出）。
- 影响：只影响退出瞬间，不影响游戏。

### 2. 加载配置时的无锁竞态 —— 代码推断，概率低

启动顺序（`main.cpp`）：

```
3748  connectDevices();      ← 轮询线程开始跑 1000 Hz
3750  SetCallback(...);      ← 回调装上了
3758  do_RESET_MAPPINGS()    ← 开始解析 OnReset.txt
3779  loadConfigFile(argv)   ← 开始解析你的 BFUI.txt
```

解析配置时会执行 `ZL,FAAL_SIGN_CHANGE_THR = 0` 这类写法，它要往一个 `std::map` 里 **插入**条目；
与此同时轮询线程每帧都在同一个 map 上做 **查找**。标准容器不支持一边写一边读。

- 会发生什么：插入只改指针、不搬动节点，所以通常只是**某几帧读到旧值/临时值**；
  但如果命令里有“删除和弦（`X,设置 = NONE`）”，会释放节点，这时并发查找就可能访问已释放内存 → 崩溃。
- 概率：每次启动都有窗口（几十毫秒），但真正撞上的概率很低，典型的“几十次启动崩一次”。
- 这是上游代码就有的，不是 FAAL 引入的；你的配置里有 5 行和弦写法，所以你在暴露面上。

### 3. 重置滤波器与轮询线程竞争 —— 代码推断，影响单帧

`RESET_MAPPINGS`（`main.cpp:1824`）和 `ONE_EURO_FILTER`（`main.cpp:1947`）会在主线程直接调用
`ResetFaalFilter()`，把正在被轮询线程读写的状态清零。

- 会发生什么：单帧状态被撕裂，理论上可能出现一帧异常输出（光标轻微跳一下）。
- 概率：只在这两条命令执行的那一瞬，通常你也不会在瞄准时敲它们。

### 4. 我加的记录功能也有同样的竞争 —— 我引入的，需要修

`FAAL_TRACE_START/STOP` 在主线程改标志和计数，记录在轮询线程。
我把缓冲区设计成“只分配不释放”，所以**不会**出现 use-after-free；
最坏情况是 CSV 尾部混进半帧数据，或某一帧没被写进去。

### 5. 回调里抛异常 = 直接崩溃 + 死锁 —— 代码推断

`joyShockPollCallback` 一进来就 `lock()`（`main.cpp:449`），退出时才 `unlock()`（1690）。
中间的 `jc->getSetting(SettingID::FAAL_...)` 在找不到该设置时**会抛 `out_of_range`**
（`JoyShock.cpp:178`），而回调没有 try/catch，锁也不会释放。

- 现在不会发生（12 个设置都注册了）。
- 但它的意思是：**任何一次注册疏漏都会变成“启动即崩”，而不是编译报错**。属于脆弱性，不是现存故障。

### 6. 头文件文档和实现对不上 —— 代码不合理

`FaalParams` 注释里把 `dropSensitivity / dropCurve / peakMinTrigger / suppressThr / freezeOutMul`
写成可调参数（`faal_filter.h:34-50`），但 `main.cpp:495-499` **每帧都硬编码覆盖**它们。
将来谁加一条 `FAAL_DROP_SENSITIVITY` 命令，会发现“改了没反应”。

## 三、性能：没有发现问题（有实测）

用你 61 秒的甩枪数据统计帧间隔：

| 帧间隔 | 帧数 | 占比 |
|---|---|---|
| < 1.2 ms | 61,916 | **99.08%** |
| 1.2 – 2 ms | 572 | 0.92% |
| > 2 ms | 0 | **0** |

62,488 帧里没有一帧超过 2 ms，遥测（UDP）也开着。说明 **1 kHz 的循环完全跑得动，FAAL 不是瓶颈**。

粗算每帧成本：12 次设置查询（每次一次哈希查找 + 一次 `dynamic_cast`）≈ 1.2 µs，
滤波本身约 50 次浮点运算，记录开启时再写 32 字节内存 → 合计远低于 1 ms 预算。

内存：滤波状态约 200 字节；记录缓冲区 6.4 MB，只在开启记录时分配，不释放（可接受）。

## 四、你的问题：“参数运行时改”这个设计对不对

**对，而且是你这套东西里做得最规范的部分。** 三点保证：

1. 每帧重新读取 12 个设置（`main.cpp:479-492`），所以 `FAAL_* = 值` 改完**下一帧就生效**；
2. 走的是 `jc->getSetting()`，也就是**按手柄 + 按和弦**解析，所以 `ZL,FAAL_SIGN_CHANGE_THR = 0`
   这种写法是真的只在按住 ZL 时生效，你的三段数据里也验证到了（默认模式 vs ZL 模式抑制率不同）；
3. 设置本身有 `SettingID` 枚举 + `SettingsManager` 注册，序列化/默认值/重置都走统一通道。

需要注意的三点（都不是“错”，是“要知道”）：

- 读写没有加锁：主线程写 float、轮询线程读 float，x86 上不会读到“半个数”，
  实践中安全，但标准上属于数据竞争；要彻底干净可以改成原子或加锁。
- 改参数**不会重置滤波器状态**：比如你把 `FAAL_PEAK_DECAY_TIME` 从 0.065 改成 0.02，
  峰值跟踪器会带着旧值平滑过渡，不会立刻生效到新稳态（几百毫秒内）。
- 有 5 个参数（drop/curve/peakmin/suppressThr/freezeMul）根本没有暴露成命令，
  而且每帧被硬编码覆盖——见问题 6。
